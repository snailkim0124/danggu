## Requirements Summary

사용자가 모바일 웹에서 4구 당구대 사진 1장을 업로드하면, 시스템이 테이블 경계와 공 4개(흰공1/노랑공1/빨간공2)를 완전 자동으로 인식하고, 직접샷부터 뱅킹샷·고급 기술샷(스핀 포함)까지 모든 가능한 캐롬 경로를 계산해, 기술 난이도 기준 상위 3개 후보를 실전에서 바로 따라칠 수 있는 수준의 수치와 함께 정적 2D 다이어그램으로 보여준다. 점수 기록/멀티플레이어/개인화 설문은 이번 버전 범위에서 제외한다.

## Key Decisions (이번 세션에서 확정)

| # | 결정 | 근거 |
|---|------|------|
| D1 | **고급기술샷(끌어치기/밀어치기/회전) v1 포함 유지** — 원래 인터뷰 결정 그대로 | 사용자가 Analyst 리스크 브리핑 이후에도 명시적으로 유지 선택. Shot 데이터 모델과 물리 엔진 범위를 이에 맞춰 확장해야 함 |
| D2 | **MVP "적중" = 득점(큐볼이 빨간공 2개 모두 접촉, 상대공 파울 없음)**, 10건 테스트 배치 구성을 사전 고정 | 기존 정의("제시된 경로대로 치면 맞다")는 시스템 오류와 사용자 실행 오류를 구분 못함. 득점 기준 + 고정 배치가 재현 가능한 판정 기준 |
| D3 *(v2 추가)* | **플레이 게이트는 단일 테스터(본인) 고정, 배치·시도횟수·휴식조건을 사전 문서화** | 복수 테스터를 섞으면 스킬 편차가 시스템 정확도 측정치에 섞여 들어가 재현 불가능해짐. 단일 테스터로 고정하고 조건을 문서화해야 이후 재실행/비교가 가능 |
| D4 *(v2 추가)* | **근접 샷(fallback)은 정량 임계값 기반 자동 판정** — "가장 근접한 샷"을 difficultyScore가 아니라 별도의 오차 지표(missMargin)로 정의 | "근접"이 정성적 표현으로만 남아있으면 구현 시 개발자마다 다르게 해석. 목적구 중심 대비 이탈 각도를 정량 지표로 명시해야 일관된 fallback 로직 구현 가능 |

## 채택된 엔지니어링 기본값 (Analyst 권고 반영, 낮은 리스크 — 필요시 언제든 재검토 가능)

- **힘(force) 표현**: 연속 수치(m/s 등) 대신 관찰 가능한 **이산 3~5단계**로 표현 (예: "쿠션 1개 돌 세기" ~ "쿠션 3개 돌 세기"). 절대 물리량은 재현 불가능하지만 이산 단계는 사람이 재현 가능.
- **테이블 규격 설정값 추가**: 대대(2540×1270mm) / 중대(2438×1219mm) 프리셋을 큐볼 색상과 함께 설정에 저장. 사진만으로는 절대 스케일 복원이 불가능하므로 힘 계산에 필요.
- **인식 확인 화면 분리**: "원본 사진 위에 인식된 공/경계를 오버레이해서 사용자가 확인·보정하는 화면"과 "결과를 보여주는 정적 다이어그램 화면"을 별개 단계로 둔다. 확인 화면이 없으면 큐볼 색상 오인식(전체 추천이 조용히 100% 틀리는 치명적 실패)을 사용자가 알아챌 방법이 없음.
- **테스트를 2단계 게이트로 분리**: (a) 지오메트릭 게이트 — 인식 정확도만 측정(사람 개입 없음), (b) 플레이 게이트 — D2 기준 실전 적중률. 지오메트릭 게이트를 먼저 통과시켜야 플레이 게이트 결과가 의미를 가짐.

## Architecture / Data Model

### Photo *(v2: recognitionStatus 필드 추가)*
| 필드 | 설명 |
|------|------|
| image | 업로드된 원본 이미지 |
| viewAngle | 비스듬한 시점 지원 여부 |
| platform | 모바일 웹 |
| **recognitionStatus** | *(v2 추가)* 인식 파이프라인 상태를 나타내는 열거값: `pending`(처리중) → `recognized`(자동 인식 성공, 신뢰도 임계값 이상) → `uncertain`(신뢰도 미달, 확인/보정 화면 필요) → `manuallyCorrected`(사용자가 터치 보정 완료) → `failed`(인식 자체 불가, 재촬영 안내). User Flow의 "불확실 시 보정" 분기를 데이터 모델 레벨에서 명시적으로 표현 |
| calibrationConfidence | 0~1 신뢰도 수치 — 임계값 미만이면 recognitionStatus가 `uncertain`으로 전이 |

### Shot (확장, v2: missMargin 추가)
| 필드 | 설명 |
|------|------|
| technique | direct / bank(N쿠션) / advanced(스핀) |
| aimTarget | 목적구 위 조준점(두께 비율) — "실전에서 따라칠 수 있는" 1차 표현. 각도(도)는 보조 표시 |
| angleDeg | 각도 수치(보조 표시) |
| forceLevel | 이산 단계(1~5) |
| tipOffset | {vertical, horizontal} — 고급기술(스핀)용, v1 direct/bank는 항상 center |
| thickness | 두께 비율 (1/2, 1/4 등) |
| sequence | 맞히는 공 순서 |
| difficultyScore | **각도-허용폭(angular tolerance)** 기반 연속 점수. 기술종류(technique)를 1차 정렬키로, 허용폭을 2차(tie-break)로 사용 |
| ruleValid | 규칙 필터(양쪽 빨간공 접촉 + 상대공 무접촉 + 경로 비폐색) 통과 여부 — false면 정상 후보에서 제외, fallback 후보 풀로만 사용 |
| **missMargin** | *(v2 추가)* `ruleValid=false`인 후보에 한해, 목표 접촉점(빨간공 2개 모두 접촉 조건) 대비 실제 궤적이 벗어나는 최소 각도 오차(도 단위). fallback 샷은 이 값이 가장 작은(=가장 근접한) 후보로 자동 선정. 값이 클수록 "근접하지 않음"으로 간주해 표시하지 않을 수 있음(임계값은 Phase 5 실측 후 튜닝) |
| confidence | 이 샷 추천의 신뢰도(인식 오차 대비 허용폭이 좁으면 낮음 → low-confidence 표시 또는 억제) |

### Table
| 필드 | 설명 |
|------|------|
| boundary | **쿠션 노즈 라인**(공이 실제로 구르는 안쪽 경계) 기준 4개 선분 — 코너 점이 아니라 4변 직선의 교점으로 계산(모서리가 프레임 밖으로 잘려도 복원 가능) |
| size | 대대 / 중대 프리셋 (설정값) |

### Ball
| 필드 | 설명 |
|------|------|
| position | 클로스 평면(z=0)이 아닌 **z=공 반지름 평면**으로 역투영 보정된 실측 좌표 |
| color | 흰/노랑/빨강×2 — 흰/노랑은 **두 후보 간 상대적 색상 비교**로 분류(절대 임계값 금지, 조명에 취약) |
| role | cueBall(설정값 기반) / opponentBall / targetBall×2 |

### CalibrationConfidence
- 인식 신뢰도 수치화 → 임계값 미만이면 Photo.recognitionStatus가 `uncertain`으로 전이하며 사진 오버레이 확인/보정 화면으로 분기

## Implementation Steps

### Phase 0 — 스캐폴딩
1. 웹 프론트엔드 프로젝트 초기화 (모바일 브라우저 카메라/파일 업로드 지원)
2. Vision/Path Calc를 처리할 백엔드 또는 서버리스 모델 서비스 골격
3. 설정 저장소(큐볼 색상 + 테이블 규격 프리셋) — 로컬 스토리지 또는 경량 서버 설정

### Phase 1 — Vision Recognition (시차 보정을 처음부터 반영, 나중에 추가하는 리팩터링 아님)
1. 쿠션 4변 라인 검출 → 교점으로 테이블 경계 산출 (코너 아웃오브프레임 대응)
2. 호모그래피 계산 및 카메라 포즈 복원
3. 공 4개 검출 → **z=반지름 평면**으로 역투영해 실측 좌표 산출
4. 흰/노랑 상대색상 분류, 빨간공 2개 식별
5. 인식 신뢰도(calibrationConfidence) 산출 → **`Photo.recognitionStatus`를 `recognized`/`uncertain`/`failed`로 전이**, 임계값 미만 시 사진 오버레이 확인/보정 화면(터치 기반) 표시 → 사용자 보정 완료 시 `manuallyCorrected`로 전이
6. **검증**: 지오메트릭 게이트용 mm 오차 측정 하네스 구축 (Phase 5에서 사용)

### Phase 2 — Path Calculation
1. 아핑-각도 스윕 기반 직접샷 후보 열거 + 규칙 필터(양쪽 빨간공 접촉/상대공 무접촉/비폐색) 적용
2. 1~2쿠션 뱅킹샷 후보 — 쿠션 반사각 계산(반발계수 근사치 포함, 이산 forceLevel과 연동)
3. 고급기술샷(스핀) 후보 — tipOffset/thickness 기반, 스로우(throw)·스쿼트(squirt) 근사 모델. **범위가 크므로 direct+bank가 지오메트릭 게이트를 통과한 뒤 별도 스프린트로 진행**
4. 각 후보의 angular-tolerance 기반 difficultyScore 산출 → 기술종류 1차 정렬, tolerance 2차 정렬
5. **유효 후보(ruleValid=true) 0개 시**: `ruleValid=false` 후보들의 missMargin을 계산해 가장 작은 값을 가진 후보를 근접 샷(fallback)으로 선정해 참고용으로 제시

### Phase 3 — Result Visualization
1. 정적 2D 다이어그램 렌더링 (테이블/공/경로 재구성)
2. 상위 3개 후보 탭/스와이프 전환 UI
3. low-confidence 후보 시각적 구분 표시
4. fallback(근접 샷)인 경우 "참고용 — 성공 가능성 낮음" 등 명시적 라벨 표시(missMargin 값 기반)

### Phase 4 — 설정 & 온보딩
1. 큐볼 색상 프리셋 UI
2. 테이블 규격(대대/중대) 프리셋 UI

### Phase 5 — 검증 (D2, D3, D4 반영)
1. **지오메트릭 게이트**: 다양한 배치의 실제 사진 N≥30장을 탑뷰 정답 사진과 대조해 공 중심/경계 mm 오차 측정. 오차 임계값(예: ≤8mm RMS) 이하일 때만 플레이 게이트 진행
2. **플레이 게이트 측정 프로토콜 (D3, v2 구체화)**:
   - **테스터**: 단일 테스터(본인) 고정 — 세션 간 스킬 편차를 통제하기 위해 복수 테스터 사용하지 않음
   - **배치**: 10건 사전 고정 (직접샷 6 / 1쿠션 뱅킹 3 / 무해(no-solution) 1)
   - **시도 횟수**: 배치당 3회 시도, 3회 중 1회라도 득점하면 해당 배치 "적중"으로 판정
   - **조건 통제**: 동일 당구대, 동일 공 세트, 연속 세션 내 진행(휴식으로 인한 컨디션 변화 최소화), 배치 순서는 매 세션 무작위화해 학습 효과로 인한 편향 방지
   - **베이스라인 병행 기록**: 동일 10건 배치에서 테스터 본인이 시스템 추천 없이 직접 선택한 샷의 성공률도 함께 기록해, 시스템 추천이 순수 실력 대비 실질적 이득을 주는지 비교
   - **적중(D2)**: 큐볼이 빨간공 2개 모두 접촉 + 상대공 파울 없음 = 득점
3. 목표: 고정 10건 중 7건(70%) 이상 적중, 테스터 베이스라인과 함께 결과 기록

## Risks and Mitigations

| 리스크 | 실패 시나리오 | 완화책 |
|--------|--------------|--------|
| 공 반지름 시차 미보정 | 2m 거리 공이 60~90mm(공 1~1.5개) 밀려 보임 → 각도 오차 ~4.5° | Phase 1에서 z=반지름 평면 역투영을 최초 설계에 반영(사후 패치 아님) |
| 힘(force) 물리 예측 불가 변수 의존 | 쿠션 반발계수·클로스 마찰이 사진에서 관측 불가 → 연속 수치가 거짓 정밀도 | 이산 forceLevel로 표현, 반발계수는 근사 상수 + 실측 보정 |
| 고급기술샷 데이터 모델 미표현 | angle+force만으론 스핀 샷 표현 불가 | Shot에 tipOffset/thickness 필드 추가(D1에 따라 v1부터 구현) |
| 인접 테이블/색상 오분류로 큐볼 스왑 | 전체 추천이 100% 틀리지만 겉보기엔 정상 | 상대색상 분류 + 사진 오버레이 확인 화면 필수 |
| 후보 생성이 파울 샷을 걸러내지 못함 | 상대공 접촉/한쪽 빨간공만 접촉하는 무효 샷 추천 | ruleValid 하드 필터(양쪽 빨간공 접촉 + 상대공 무접촉 + 비폐색) |
| N=10 플레이 테스트가 통계적으로 저신뢰 | 완벽한 시스템도 배치 구성에 따라 70% 미달 가능 | 지오메트릭 게이트로 시스템 정확도 별도 검증, 배치 구성 사전 고정, 인간 베이스라인 병행 기록 |
| **(v2)** 복수 테스터/비일관 조건으로 플레이 게이트 결과가 재현 불가능해짐 | 다른 사람이 치면 적중률이 달라져 시스템 성능인지 사람 실력인지 구분 불가 | D3: 단일 테스터·고정 배치·고정 시도횟수·조건 통제를 프로토콜로 문서화(Phase 5 §2) |
| **(v2)** "근접 샷"이 정성적 판단에 의존해 구현마다 다르게 동작 | 개발자·버전마다 다른 fallback 샷이 선택되어 사용자 경험 불일치 | D4: missMargin(목표 접촉 조건 대비 최소 각도 오차)을 Shot 필드로 정의, 최솟값 후보를 자동 선정 |
| **(v2)** 인식 실패/불확실 상태가 코드 레벨에서 암묵적으로만 처리됨 | 상태 전이 로직이 산발적으로 구현되어 엣지케이스(재시도, 타임아웃) 누락 가능 | Photo.recognitionStatus 열거형으로 상태를 명시적으로 모델링(Phase 1 §5) |

## Verification Steps

- [ ] 지오메트릭 게이트: mm 오차 임계값 이하 달성 (측정 하네스로 재현 가능)
- [ ] 규칙 필터 단위 테스트: 상대공 접촉/한쪽만 접촉하는 경로가 정상 후보에서 제외되는지 확인
- [ ] 흰/노랑 분류가 다양한 조명 샘플에서 상대색상 기준으로 안정적인지 확인
- [ ] `Photo.recognitionStatus`가 신뢰도 임계값에 따라 `recognized`/`uncertain`/`failed`로 올바르게 전이하는지, `uncertain` 시 확인/보정 화면이 실제로 트리거되는지 확인
- [ ] 사용자가 보정 완료 시 `recognitionStatus`가 `manuallyCorrected`로 전이하는지 확인
- [ ] `missMargin` 계산 단위 테스트: 유효 후보 0개인 배치에서 missMargin이 가장 작은 후보가 fallback으로 선정되는지 확인
- [ ] 플레이 게이트: 프로토콜(단일 테스터, 고정 10건 배치, 배치당 3회 시도, 조건 통제) 준수 하에 득점 기준 채점 결과 70%+ 달성, 테스터 베이스라인과 함께 기록
- [ ] 유효 후보 0개 배치에서 근접 샷 fallback이 "참고용" 라벨과 함께 표시되는지 확인
