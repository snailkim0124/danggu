## Requirements Summary

사용자가 모바일 웹에서 4구 당구대 사진 1장을 업로드하면, 시스템이 테이블 경계와 공 4개(흰공1/노랑공1/빨간공2)를 완전 자동으로 인식하고, 직접샷부터 1쿠션·2쿠션 이상·뱅크샷까지 모든 가능한 캐롬 경로를 계산해(회전은 기술 종류와 무관한 독립 속성), 기술 난이도 기준(사용자 개인화 설문으로 보정됨) 상위 3개 후보를 실전에서 바로 따라칠 수 있는 수준의 수치와 함께 정적 2D 다이어그램으로 보여준다. 점수 기록/멀티플레이어는 이번 버전 범위에서 제외한다. *(2026-08-30 정정: "고급 기술샷"과 "개인화 설문 제외"는 D1/D5 개정으로 더 이상 유효하지 않음 — 위 변경 이력 참고)*

D1의 "고급기술샷"이라는 4번째 기술 계층 자체가 혼동의 원인이었음 — 회전 여부와 기술 난이도(쿠션 횟수)는 서로 독립적인 축이라는 게 실전에서 드러남 |
| D2 | **MVP "적중" = 득점(큐볼이 빨간공 2개 모두 접촉, 상대공 파울 없음)**, 10건 테스트 배치 구성을 사전 고정 | 기존 정의("제시된 경로대로 치면 맞다")는 시스템 오류와 사용자 실행 오류를 구분 못함. 득점 기준 + 고정 배치가 재현 가능한 판정 기준 |
| D3 *(v2 추가)* | **플레이 게이트는 단일 테스터(본인) 고정, 배치·시도횟수·휴식조건을 사전 문서화** | 복수 테스터를 섞으면 스킬 편차가 시스템 정확도 측정치에 섞여 들어가 재현 불가능해짐. 단일 테스터로 고정하고 조건을 문서화해야 이후 재실행/비교가 가능 |
| D4 *(v2 추가)* | **근접 샷(fallback)은 정량 임계값 기반 자동 판정** — "가장 근접한 샷"을 difficultyScore가 아니라 별도의 오차 지표(missMargin)로 정의 | "근접"이 정성적 표현으로만 남아있으면 구현 시 개발자마다 다르게 해석. 목적구 중심 대비 이탈 각도를 정량 지표로 명시해야 일관된 fallback 로직 구현 가능 |
| D5 *(2026-08-30 추가)* | **개인화 난이도 설문을 v1로 앞당김** — PRD Non-Goals의 "v2 이후"를 뒤집고 끌어치기/밀어치기/얇게치기/회전/뱅크샷/3쿠션 이상 6개 항목(1~5점) 설문을 v1에 구현 | "설문조사 기능이 없어서 추가해야함"이라는 실사용 피드백. 고정 기술위계만으로는 개인 실력차를 반영 못해 추천이 비현실적으로 느껴짐 |
| D6 *(2026-08-30 추가)* | **키스(의도치 않은 다른 공과의 충돌) 회피를 confidence에 반영** — 맞은 공의 진행선이 다른 공에 가까울수록 연속적으로 confidence 감점(하드 필터 아님), 근접거리 휴리스틱으로 구현(정밀 2차 충돌 시뮬레이션 아님) | 최초 PRD/PLAN에 없던 gap. 큐볼-공 충돌은 이미 모델링돼 있었으나 "맞은 공이 다른 공을 건드리는" 2차 충돌은 전혀 반영되지 않고 있었음(Deep Interview로 범위 확정, 앰비규어티 59%→13.25%) |

## 채택된 엔지니어링 기본값 (Analyst 권고 반영, 낮은 리스크 — 필요시 언제든 재검토 가능)

- **힘(force) 표현**: 연속 수치(m/s 등) 대신 관찰 가능한 **이산 3~5단계**로 표현 (예: "쿠션 1개 돌 세기" ~ "쿠션 3개 돌 세기"). 절대 물리량은 재현 불가능하지만 이산 단계는 사람이 재현 가능.
- **테이블 규격 설정값 추가**: 대대(2540×1270mm) / 중대(2438×1219mm) 프리셋을 큐볼 색상과 함께 설정에 저장. 사진만으로는 절대 스케일 복원이 불가능하므로 힘 계산에 필요.
- **인식 확인 화면 분리**: "원본 사진 위에 인식된 공/경계를 오버레이해서 사용자가 확인·보정하는 화면"과 "결과를 보여주는 정적 다이어그램 화면"을 별개 단계로 둔다. 확인 화면이 없으면 큐볼 색상 오인식(전체 추천이 조용히 100% 틀리는 치명적 실패)을 사용자가 알아챌 방법이 없음.
- **테스트를 2단계 게이트로 분리**: (a) 지오메트릭 게이트 — 인식 정확도만 측정(사람 개입 없음), (b) 플레이 게이트 — D2 기준 실전 적중률. 지오메트릭 게이트를 먼저 통과시켜야 플레이 게이트 결과가 의미를 가짐.

## Architecture / Data Model

### Photo *(2026-08-30: 계획했던 `recognitionStatus` 열거형 대신 실제 구현된 필드로 정정)*
| 필드 | 설명 |
|------|------|
| image | 업로드된 원본 이미지 |
| viewAngle | 비스듬한 시점 지원 여부 |
| platform | 모바일 웹 |
| **confidence** | *(구현됨 — 계획한 `recognitionStatus` 열거형 대신)* 0~1 신뢰도 수치(`RecognitionResult.confidence`). `pending`/`failed` 상태는 별도 열거값이 아니라 비동기 로딩 상태·예외 처리(디코딩/인식 실패 시 throw)로 처리됨 |
| **needsManualCorrection** | *(구현됨)* `confidence`가 `CONFIDENCE_THRESHOLD` 미만이면 true — User Flow의 "불확실 시 보정" 분기를 이 boolean 하나로 표현. 사용자가 보정 화면에서 "확정"을 누르면 이 값을 false로 설정해 넘김(별도 `manuallyCorrected` 상태값은 없음). 5단계 열거형보다 단순하지만 실사용 검증 결과 상태 전이 누락 없이 동작 확인됨(`lib/vision/realPhotos.test.ts`) |

### Shot (2026-08-30: `technique`/`tipOffset` 정정 — §Key Decisions D1 개정, `missMargin` 실제 구현으로 정정)
| 필드 | 설명 |
|------|------|
| technique | *(정정)* `direct` / `bank1`(1쿠션) / `bank2plus`(2쿠션 이상) / `bankShot`(뱅크샷·빈쿠션치기) — 순전히 큐볼 경로의 쿠션 접촉 횟수/순서로만 결정. "advanced(고급기술)" 계층은 폐지됨 |
| aimTarget | 목적구 위 조준점(두께 비율) — "실전에서 따라칠 수 있는" 1차 표현. 각도(도)는 보조 표시 |
| angleDeg | 각도 수치(보조 표시) |
| forceLevel | 이산 단계(1~5) |
| tipOffset | *(정정)* {vertical, horizontal} — `technique`과 무관하게 모든 샷에 적용 가능한 독립 속성(끌어치기/밀어치기/좌우 회전). "고급기술 전용" 아님 — direct/bank1/bank2plus/bankShot 어느 것이든 center가 아닌 tipOffset을 가질 수 있음 |
| thickness | 두께 비율 (1/2, 1/4 등) — UI에서는 8분위 기약분수로 표시(예: 2/8→1/4) |
| sequence | 맞히는 공 순서 |
| difficultyScore | **각도-허용폭(angular tolerance)** 기반 연속 점수. 기술종류(technique, 사용자 skillProfile로 개인화됨 — §D5)를 1차 정렬키로, 허용폭을 2차(tie-break)로 사용 |
| ruleValid | 규칙 필터(양쪽 빨간공 접촉 + 상대공 무접촉 + 경로 비폐색) 통과 여부 — false면 정상 후보에서 제외, fallback 후보 풀로만 사용 |
| **missDistanceMm** *(계획의 `missMargin`을 실제 구현명으로 정정)* | `Shot` 위가 아니라 pathcalc 내부 `SimulationResult.missDistanceMm`에 존재 — 아직 접촉하지 못한 적구까지 큐볼 중심이 도달했던 최근접 거리(mm 단위, 각도가 아님)의 합. `ruleValid=false`인 후보 중 이 값이 가장 작은(=가장 근접한) 후보가 fallback으로 자동 선정됨(`nearMissPenalty`가 파울에는 큰 페널티를 추가로 부과) |
| confidence | 이 샷 추천의 신뢰도(인식 오차 대비 허용폭이 좁으면 낮음 → low-confidence 표시 또는 억제). *(2026-08-30 추가, D6)* 맞은 공의 진행선이 다른 공에 가까울수록(키스 위험) 연속적으로 추가 감점됨 |

## Implementation Steps

### Phase 0 — 스캐폴딩 ✅ 완료
1. 웹 프론트엔드 프로젝트 초기화 (모바일 브라우저 카메라/파일 업로드 지원)
2. Vision/Path Calc를 처리할 백엔드 또는 서버리스 모델 서비스 골격
3. 설정 저장소(큐볼 색상 + 테이블 규격 프리셋) — 로컬 스토리지 또는 경량 서버 설정

### Phase 1 — Vision Recognition (시차 보정을 처음부터 반영, 나중에 추가하는 리팩터링 아님) ✅ 완료 (+계획에 없던 개선 포함)
1. 쿠션 4변 라인 검출 → 교점으로 테이블 경계 산출 (코너 아웃오브프레임 대응). *(2026-08-30 추가)* 쿠션이 바닥 천과 같은 색이라 색상만으론 노즈선을 못 찾는 문제를 발견해, 검출된 바깥 경계를 쿠션 폭만큼 안쪽으로 보정 + 사진 위 모서리 드래그로 재보정 가능하게 함
2. 호모그래피 계산 및 카메라 포즈 복원
3. 공 4개 검출 → **z=반지름 평면**으로 역투영해 실측 좌표 산출. *(2026-08-30 추가)* 공 2개가 붙어있으면 하나의 얼룩으로 합쳐져 인식 실패하던 문제를 발견해, 국소 영역에 한해 `HoughCircles`로 재분리하는 로직 추가(그림자·글레어를 공으로 오인식하는 2차 버그도 실제 사진 기반으로 발견·수정)
4. 흰/노랑 상대색상 분류, 빨간공 2개 식별
5. 인식 신뢰도 산출 → **`needsManualCorrection` boolean으로 전이** (계획한 `recognitionStatus` 5단계 열거형 대신 — 위 Photo 섹션 참고), 임계값 미만 시 사진 오버레이 확인/보정 화면(터치 기반) 표시
6. **검증**: 지오메트릭 게이트용 mm 오차 측정 하네스 구축 완료(`scripts/geometric-gate.ts`) — 합성 사진 5건은 통과(RMS 3.12mm)했으나 계획이 요구하는 실제 사진 N≥30장 검증은 아직 없음(Phase 5 참고). 실제 사진 기반 회귀 테스트는 별도로 존재(`lib/vision/realPhotos.test.ts`, `scripts/diagnose-recognition.ts`)

### Phase 2 — Path Calculation ✅ 완료 (기술 계층 D1 개정 반영 + 키스 회피 D6 추가)
1. 아핑-각도 스윕 기반 직접샷 후보 열거 + 규칙 필터(양쪽 빨간공 접촉/상대공 무접촉/비폐색) 적용
2. 1~2쿠션 후보 — 쿠션 반사각 계산(반발계수 근사치 포함, 이산 forceLevel과 연동). 뱅크샷(쿠션을 먼저 맞히는 경우)은 별도 최하위 기술로 분류(§D1 개정)
3. ~~고급기술샷(스핀) 후보~~ *(D1 개정으로 폐지)* — 회전(tipOffset)은 모든 기술에 독립적으로 적용되는 속성으로 재구현되어 direct/bank1/bank2plus/bankShot 어디에도 붙을 수 있음. 스로우/스쿼트 근사는 여전히 미구현(Open Follow-ups 참고)
4. 각 후보의 angular-tolerance 기반 difficultyScore 산출 → 기술종류(사용자 skillProfile로 개인화, §D5) 1차 정렬, tolerance 2차 정렬
5. **유효 후보(ruleValid=true) 0개 시**: `ruleValid=false` 후보들의 missDistanceMm(계획의 missMargin — 위 Shot 섹션 참고)을 계산해 가장 작은 값을 가진 후보를 근접 샷(fallback)으로 선정해 참고용으로 제시
6. *(2026-08-30 추가, §D6)* **키스(의도치 않은 다른 공과의 충돌) 회피** — 맞은 공의 진행선이 다른 공에 가까울수록 해당 후보의 confidence를 연속적으로 감점(하드 필터 아님), 근접거리 휴리스틱으로 구현

### Phase 3 — Result Visualization ✅ 완료

2. 상위 3개 후보 탭/스와이프 전환 UI

2. 테이블 규격(대대/중대) 프리셋 UI

### Phase 5 — 검증 (D2, D3, D4 반영) 🔶 진행 중 — MVP 완성 판정 미달성
1. **지오메트릭 게이트**: 다양한 배치의 실제 사진 N≥30장을 탑뷰 정답 사진과 대조해 공 중심/경계 mm 오차 측정. 오차 임계값(예: ≤8mm RMS) 이하일 때만 플레이 게이트 진행.
   **현황**: 하네스는 구축 완료(`scripts/geometric-gate.ts`)했고 합성 사진 5건은 통과(RMS 3.12mm)했으나, **계획이 요구하는 실제 사진 N≥30장 검증은 아직 0건** — 지금까지의 실제 사진 2장(`scripts/fixtures/photos/`)은 버그 재현·회귀 테스트용이지 ground-truth 좌표를 갖춘 지오메트릭 게이트용 세트가 아님
2. **플레이 게이트 측정 프로토콜 (D3, v2 구체화)**:
   - **테스터**: 단일 테스터(본인) 고정 — 세션 간 스킬 편차를 통제하기 위해 복수 테스터 사용하지 않음
   - **배치**: 10건 사전 고정 (직접샷 6 / 1쿠션 뱅킹 3 / 무해(no-solution) 1)
   - **시도 횟수**: 배치당 3회 시도, 3회 중 1회라도 득점하면 해당 배치 "적중"으로 판정
   - **조건 통제**: 동일 당구대, 동일 공 세트, 연속 세션 내 진행(휴식으로 인한 컨디션 변화 최소화), 배치 순서는 매 세션 무작위화해 학습 효과로 인한 편향 방지
   - **베이스라인 병행 기록**: 동일 10건 배치에서 테스터 본인이 시스템 추천 없이 직접 선택한 샷의 성공률도 함께 기록해, 시스템 추천이 순수 실력 대비 실질적 이득을 주는지 비교
   - **적중(D2)**: 큐볼이 빨간공 2개 모두 접촉 + 상대공 파울 없음 = 득점
   - **현황**: 1차 실행 완료(2026-08-29, `docs/testing/play-gate-results-2026-08-29.md`) — **적중률 60%**(목표 미달), 좌표를 줄자로 실측하지 않고 진행되어 재현성이 낮음. "시도 3회"도 프로토콜(같은 샷 3회)과 다르게 상위 3개 후보를 각 1회씩 시도하는 방식으로 실제 진행됨(기록에 명시)
3. 목표: 고정 10건 중 7건(70%) 이상 적중, 테스터 베이스라인과 함께 결과 기록 — **미달성 (현재 60%)**

## Risks and Mitigations

| 리스크 | 실패 시나리오 | 완화책 |
|--------|--------------|--------|
| 공 반지름 시차 미보정 | 2m 거리 공이 60~90mm(공 1~1.5개) 밀려 보임 → 각도 오차 ~4.5° | Phase 1에서 z=반지름 평면 역투영을 최초 설계에 반영(사후 패치 아님) |
| 힘(force) 물리 예측 불가 변수 의존 | 쿠션 반발계수·클로스 마찰이 사진에서 관측 불가 → 연속 수치가 거짓 정밀도 | 이산 forceLevel로 표현, 반발계수는 근사 상수 + 실측 보정 |
| 회전(스핀) 데이터 모델 미표현 | angle+force만으론 스핀 샷 표현 불가 | Shot에 tipOffset/thickness 필드 추가 — *(D1 개정)* 별도 기술 계층이 아니라 모든 technique에 적용 가능한 독립 속성으로 구현 |
| 인접 테이블/색상 오분류로 큐볼 스왑 | 전체 추천이 100% 틀리지만 겉보기엔 정상 | 상대색상 분류 + 사진 오버레이 확인 화면 필수 |
| 후보 생성이 파울 샷을 걸러내지 못함 | 상대공 접촉/한쪽 빨간공만 접촉하는 무효 샷 추천 | ruleValid 하드 필터(양쪽 빨간공 접촉 + 상대공 무접촉 + 비폐색) |
| N=10 플레이 테스트가 통계적으로 저신뢰 | 완벽한 시스템도 배치 구성에 따라 70% 미달 가능 | 지오메트릭 게이트로 시스템 정확도 별도 검증, 배치 구성 사전 고정, 인간 베이스라인 병행 기록 |
| **(v2)** 복수 테스터/비일관 조건으로 플레이 게이트 결과가 재현 불가능해짐 | 다른 사람이 치면 적중률이 달라져 시스템 성능인지 사람 실력인지 구분 불가 | D3: 단일 테스터·고정 배치·고정 시도횟수·조건 통제를 프로토콜로 문서화(Phase 5 §2) |
| **(v2)** "근접 샷"이 정성적 판단에 의존해 구현마다 다르게 동작 | 개발자·버전마다 다른 fallback 샷이 선택되어 사용자 경험 불일치 | D4: missDistanceMm(목표 접촉 조건 대비 최소 거리 오차, mm 단위)을 `SimulationResult` 필드로 정의, 최솟값 후보를 자동 선정 |
| **(v2)** 인식 실패/불확실 상태가 코드 레벨에서 암묵적으로만 처리됨 | 상태 전이 로직이 산발적으로 구현되어 엣지케이스(재시도, 타임아웃) 누락 가능 | `RecognitionResult.confidence` + `needsManualCorrection` boolean으로 모델링 — *(정정)* 계획한 5단계 열거형보다 단순하지만 실사용 검증 결과 상태 누락 없이 동작 확인됨 |
| **(2026-08-30 추가)** 쿠션이 바닥 천과 같은 색이라 노즈선 위치를 색상만으로 특정 불가 | 검출된 경계가 실제보다 바깥쪽(외곽 레일)에 잡혀 모든 mm 좌표가 계통적으로 오차 | 검출된 외곽 경계를 쿠션 폭(추정치, 설정 가능)만큼 안쪽으로 자동 보정 + 사진 위에서 사용자가 모서리를 직접 드래그해 재보정 가능 |
| **(2026-08-30 추가)** 공 2개가 붙어있으면(터치/오클루전) 하나의 얼룩으로 합쳐져 인식 실패 | "공 4개 중 3개만 검출" 오류로 인식 전체 실패 | 얼룩 면적이 공 1~4.5개 범위면 국소 영역에 한해 `HoughCircles`로 재분리 시도 — 그림자·글레어 오인식 등 2차 버그는 실제 사진 기반 회귀 테스트로 방지(`lib/vision/realPhotos.test.ts`) |

## Verification Steps

- [x] 지오메트릭 게이트: mm 오차 임계값 이하 달성 — **합성 사진 5건만 검증됨**(RMS 3.12mm, `scripts/geometric-gate.ts`). 계획이 요구하는 실제 사진 N≥30장 검증은 아직 없음
- [x] 규칙 필터 단위 테스트: 상대공 접촉/한쪽만 접촉하는 경로가 정상 후보에서 제외되는지 확인
- [x] 흰/노랑 분류가 다양한 조명 샘플에서 상대색상 기준으로 안정적인지 확인
- [x] `needsManualCorrection`이 신뢰도 임계값에 따라 올바르게 true/false 전이하는지, true일 때 확인/보정 화면이 실제로 트리거되는지 확인 (계획한 `Photo.recognitionStatus` 열거형 대신 — 위 Photo 섹션 참고)
- [x] 사용자가 보정 완료 시 `needsManualCorrection`이 `false`로 전이하는지 확인
- [x] `missDistanceMm` 계산 단위 테스트: 유효 후보 0개인 배치에서 이 값이 가장 작은 후보가 fallback으로 선정되는지 확인 (계획한 `missMargin` 대신 — 위 Shot 섹션 참고)
- [ ] 플레이 게이트: 프로토콜(단일 테스터, 고정 10건 배치, 배치당 3회 시도, 조건 통제) 준수 하에 득점 기준 채점 결과 70%+ 달성, 테스터 베이스라인과 함께 기록 — **1차 실행 60%로 미달성**(`docs/testing/play-gate-results-2026-08-29.md`), 좌표 줄자 실측 없이 진행되어 재실행 필요
- [x] 유효 후보 0개 배치에서 근접 샷 fallback이 "참고용" 라벨과 함께 표시되는지 확인
