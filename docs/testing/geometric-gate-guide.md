# 지오메트릭 게이트 가이드 — 테스트 사진 및 정답 좌표 수집

지오메트릭 게이트는 **당구를 치지 않고도** 진행할 수 있는 테스트입니다. 사진과 정답 좌표만 모아서 전달하면, 나머지(오차 계산·통과/실패 판정·리포트 작성)는 Claude가 자동으로 처리합니다.

- 참고 문서: `.omc/plans/danggu-4gu-path-guide-plan.md` (Phase 5 — 지오메트릭 게이트)
- 측정 대상: **인식 정확도만** (실제 샷 성공 여부가 아님 — 그건 [`play-gate-checklist.md`](./play-gate-checklist.md)의 몫)
- 통과 기준: 공 중심 위치 오차 RMS ≤ 8mm (예시 기준값 — 최종 임계값은 하네스 리포트에서 확인)

## 1. 준비물

- 4구 당구대, 흰공/노랑공/빨간공×2
- 스마트폰 (사진 촬영용, 실제 앱 사용 환경과 동일하게)
- 줄자 (mm 또는 mm로 환산 가능한 단위)
- (선택) 삼각대나 사다리 등 탑뷰 촬영에 도움이 되는 도구

## 2. 몇 장을 어떻게 찍어야 하나

- **최소 30장(N≥30)**, 매번 공 배치를 다르게 바꿔가며 촬영
- **사람 시점(비스듬한 각도)**으로 촬영 — 실제 사용자가 앱을 쓸 때와 동일한 조건이어야 인식 정확도 측정이 의미 있습니다. 일부러 탑뷰로 찍지 마세요 (탑뷰는 정답 좌표를 구할 때만 별도로 사용, 아래 §3 참고)

> ⚠️ **촬영 각도 제한 (2026-08-30 추가 — 실사진 30장 검증 결과 반영)**: "비스듬한 각도"는 테이블 위쪽에서 아래로 거의 내려다보는 구도(폰을 높이 들고 테이블 위에서 내려찍는 것)를 뜻하지 않습니다. 실제로 이런 구도로 찍은 사진 30장을 테스트했더니 8장은 공 4개 중 일부조차 인식 못 했고, 나머지도 오차가 목표치(8mm RMS)의 수십~백 배 수준이었습니다. 원인은 카메라 자세를 사진 한 장의 테이블 모서리만으로 역산하는 방식이 이런 가파른 각도에서는 모서리 검출의 작은 오차를 크게 증폭시키기 때문입니다 (`lib/vision/table.ts`, `lib/vision/camera.ts` 참고 — 근본적으로 코너 검출 정밀도 문제라 촬영 조건을 바꾸는 게 가장 확실한 해결책입니다).
>
> **올바른 촬영법**: 당구를 실제로 칠 때처럼 테이블 옆이나 짧은 변 쪽에 서서, 폰을 눈높이~가슴 높이 정도로 들고 테이블을 가로질러 비스듬히 바라보는 구도로 찍으세요. 테이블 위쪽에서 아래로 찍거나 폰을 머리 위로 들어 내려다보는 구도는 피해주세요.
>
> **쿠션 4개의 모서리가 전부 사진 안에 실제로 보이도록** 프레임을 잡는 걸 권장합니다 — 모서리가 잘려 나가면 그 모서리는 추정값이 되는데, 가파른 각도와 겹치면 오차가 특히 커집니다. 모서리가 살짝 걸치는 정도는 괜찮지만, 테이블 전체가 한 프레임에 안 들어올 정도로 바짝 붙지는 마세요 — 필요하면 한 걸음 물러서세요.

- 다양성을 확보하세요 (단, 위 각도 제한 안에서):
  - 촬영 각도(테이블을 정면으로 마주보는 것부터 옆으로 많이 돌아간 것까지 — 상하로 가파른 정도가 아니라 좌우 회전 각도의 다양성)
  - 촬영 거리(가까이/멀리 — 단, 테이블 전체가 프레임에 들어오는 범위 안에서)
  - 조명 조건(밝음/어두움/그림자)
  - 공 배치(구석에 몰린 배치, 흩어진 배치, 서로 가까운 배치 등)
  - 테이블 규격(대대/중대 둘 다 있다면 섞어서 촬영 — 없다면 사용하는 규격으로만 진행해도 무방)

## 3. 정답 좌표를 구하는 방법 (사진마다 1세트씩 필요)

사진 속 공 4개의 **실제 중심 좌표(mm)**와 테이블 경계를 알아야 인식 결과와 비교할 수 있습니다. 아래 두 방법 중 하나를 고르세요.

### 방법 A — 자로 직접 측정 (권장, 더 정확함)

1. 테이블의 기준 코너 하나를 정합니다 (예: 왼쪽 아래 쿠션 노즈 코너 — 매 사진마다 동일한 코너를 기준으로 쓰세요).
2. 공을 배치한 뒤 사진을 찍기 **직전 또는 직후**, 각 공의 중심까지 기준 코너로부터 가로(x)·세로(y) 거리를 줄자로 재서 mm 단위로 기록합니다.
3. 테이블 자체의 가로·세로 길이도 한 번 실측해 기록해 둡니다 (대대/중대 공식 규격과 실제로 오차가 있을 수 있으므로).

### 방법 B — 탑뷰 참조 사진

1. 사람 시점 사진을 찍은 직후, 같은 배치를 건드리지 않은 상태로 **테이블 바로 위에서 수직으로 내려다본 사진**을 한 장 더 찍습니다 (사다리 등 이용).
2. 탑뷰 사진에서 테이블 경계(코너 4개)와 공 4개 중심의 픽셀 좌표를 확인한 뒤, 테이블의 알려진 실제 규격(mm)을 이용해 픽셀→mm로 환산합니다.
3. 탑뷰 사진도 완벽한 수직은 아니므로 약간의 렌즈 왜곡/기울어짐 오차가 섞일 수 있습니다 — 가능하면 방법 A와 병행하는 것을 권장합니다.

**방법 A가 더 정확합니다.** 시간이 된다면 A를 우선하고, 여러 장을 빠르게 처리해야 할 때만 B를 보조로 쓰세요.

## 4. 파일 정리 방법

사진과 정답 좌표를 짝지어 정리하세요. 예:

```
test-data/geometric-gate/
  photo-001.jpg
  photo-001.ground-truth.json
  photo-002.jpg
  photo-002.ground-truth.json
  ...
```

(정확한 폴더 위치는 `scripts/` 담당자와 맞춰도 됩니다 — 위 경로는 예시입니다.)

## 5. 정답 좌표 JSON 형식

> ✅ **확인 완료 (2026-08-30)**: `scripts/geometric-gate.ts` 하네스가 작성되었고, 아래 형식이 그 하네스가 실제로 읽는 `GroundTruth` 타입과 정확히 일치함을 확인했습니다. `scripts/fixtures/`의 합성(synthetic) 픽스처 5건으로 하네스 자체는 이미 검증됨(풀링 RMS 3.12mm, PASS). 이 문서대로 데이터를 모아 `test-data/geometric-gate/`(하네스 기본 경로)에 넣으면 바로 처리됩니다.

```json
{
  "photoFile": "photo-001.jpg",
  "table": {
    "size": "중대",
    "widthMm": 2438,
    "heightMm": 1219
  },
  "balls": [
    { "color": "white", "x": 320.5, "y": 610.2 },
    { "color": "yellow", "x": 1500.0, "y": 900.0 },
    { "color": "red1", "x": 800.0, "y": 300.0 },
    { "color": "red2", "x": 2000.0, "y": 700.0 }
  ]
}
```

- `x`, `y`는 §3에서 정한 **기준 코너로부터의 mm 거리** (x = 기준 코너에서 테이블 긴 변을 따라, y = 짧은 변을 따라 — 방법 A/B 모두 같은 기준 사용)
- `color`는 `lib/types.ts`의 `BallColor`(`'white' | 'yellow' | 'red1' | 'red2'`)와 동일한 값 사용
- `table.size`는 `TableSize`(`'대대' | '중대'`)와 동일

## 6. 완료 후

사진 + 정답 좌표 30세트 이상을 모아서 전달하면, Claude가 `scripts/geometric-gate.ts` 하네스로 각 사진을 인식시켜 정답과의 mm 오차(RMS)를 계산하고, 임계값(예: ≤8mm) 통과 여부를 자동으로 판정한 리포트를 만들어 드립니다.
